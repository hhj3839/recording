# 로그인·초기 화면 지연 진단 및 회귀 보강

기준: 2026-11-03. PR #276~#279가 main에 병합·운영 배포됐다. 아래 최초 진단과 19:24 표본은 변경 전 이력이다. 최신 운영 비교와 검증 한계는 [리전 최적화 결과](REGION_LATENCY_2026-11-03.md)를 기준으로 본다.

## 최초 진단 당시 원인과 한계

1. PR #274가 해결한 로그인 폼의 예외 후 busy 고착과 별도로, 초기 화면의 4개 API 요청에는 제한 시간이 없었다. 학급/계획은 Promise.all, 결과 집계도 별도 Promise.all로 기다린다. 하나가 응답하지 않으면 해당 그룹이 계속 로딩으로 남는다. 기존 코드로 class-data 응답을 보류하고 브라우저 시간을 20초 넘겨 진행했을 때 `확인 중`, aria-busy=true 유지로 회귀 검사가 실패했다.
2. getDataScope는 각 API마다 getAuthUser → teachers upsert → 학급 조회를 수행한다. 초기 4개 요청은 같은 인증·소유 범위 확인을 각각 거치고, 결과 집계는 학생 평어 본문·영역 상세와 행동특성 본문까지 받는다. 이는 지연을 키울 수 있는 구조이며 현재 표본만으로 특정 DB 쿼리가 병목이라고 확정하지 않는다. 인증 생략·전역 사용자 캐시·임의 스키마 변경은 하지 않았다.
3. 로그인 API도 로그인 시도 제한 조회 → 인증 → 시도 기록 정리 → 기억한 학급 확인을 직렬로 수행한다. 로그인 폼 복구와 서버 응답 속도는 별개다.
4. 기존 배포에는 단계별 Server-Timing이 없어 당시 지연을 Supabase Auth/DB/플랫폼·네트워크 중 하나로 특정할 근거가 부족하다. 현재 30분 운영 오류·경고 로그 집계는 빈 결과였고, 2시간 조회는 요금제 보존 범위 제한으로 실패했다. 오류 로그가 없다는 사실을 지연이 없다는 뜻으로 해석하지 않는다.

## 운영 시간 표본

2026-11-03 19:24:56 KST 완료. 기존 실험실 자격 증명을 이용해 로그인 1회, 초기 조회 4개를 병렬로 2회 수행했다. 응답 본문·비밀번호·쿠키는 출력하거나 저장하지 않았다. 서버의 정상 인증 이력/교사 정보 갱신은 기존 요청 경로에서 발생할 수 있으며, 학생 데이터 편집·생성 API는 호출하지 않았다.

## 수정 내용

- 초기 학급·평가계획과 결과 집계 요청에 각각 20초 제한을 추가했다. 응답 본문 읽기까지 제한이 유지되며 실패하면 오류와 `학급 현황 다시 불러오기` 버튼을 표시한다.
- 재시도 시 이전 요청을 중단하고 취소된 응답의 상태 반영을 막는다. 대시보드에서 나가면 집계 조회도 정리한다. 브라우저 중단이 이미 실행 중인 서버 처리를 취소하는 것은 아니다.
- 로그인·초기 조회 4개에 요청 범위별 `Server-Timing: total, auth, database`를 추가했다. AsyncLocalStorage로 동시 사용자 요청을 분리한다. auth는 인증 처리 함수의 전체 시간, database는 REST 호출부터 본문 처리까지의 누적 시간이다. 병렬 DB 호출의 누적값은 total보다 클 수 있으며 call 수는 계측 함수 호출 횟수다.
- `LOADING_DIAGNOSTICS=1`을 배포 환경에 명시적으로 설정하면 정해진 경로명·상태·시간·횟수만 서버 로그로 기록한다. 기본값은 로그 비활성이다. 자격 증명·사용자 ID·쿼리·응답 본문·외부 오류 원문은 새 진단 로그에 넣지 않는다. 실제 운영 환경 변수는 변경하지 않았다.
- 로그인 서버에서 예외가 나면 비밀 정보 없는 JSON 503을 반환한다. 로그인 시도 제한의 실패를 무시하고 인증을 진행하지 않으며 기존 429 정책도 유지한다.
