## 실행 순서

전체 플랫폼 리허설은 사용자가 신규 프로젝트 생성과 Docker/WSL 설치 없이 가능한 DB 검증으로 범위를 좁혔다. 해당 DB 검증은 완료했지만 실제 로그인·앱 권한·Storage API는 완료 처리하지 않는다. 전체 플랫폼 검증은 아래 환경 조건부 P1로 유지하고, 지금 진행 가능한 1번은 복원에서 드러난 소유권 누락의 원인·영향 조사로 갱신한다. 실제 운영 생성 완료 검증과 배치 장애의 멱등성은 3번, 성능 표본 확대는 4번을 유지한다.

**환경 조건부 P1 — 전체 플랫폼 복구 검증:** 사용자가 별도 Supabase 실행 환경 또는 Docker/WSL 사용을 선택하면 재개한다. 실제 Auth 로그인·토큰 흐름, 다른 교사의 학급 접근 거부, 앱 결과 조회, Storage API 및 필요한 설정·외부 연동을 검증하고 서비스 RTO를 측정한다. 현재 파일 원본은 0개이므로 실제 파일 복구는 대상 없음과 미검증을 구분한다. 이 과제는 정식 운영 전 필수이며 새 프로젝트 생성·설치·과금을 자동으로 재시도하지 않는다. 근거와 누락 범위는 [복원 리허설 기록](SUPABASE_PLATFORM_RESTORE_RUNBOOK.md)을 따른다.

## 검증 범위와 한계

- 최신 로컬 복원은 DB 스키마·데이터·관계 검사다. 관리자 SQL로 소유권 연결을 확인한 결과를 앱/API의 접근 거부 성공으로 해석하지 않는다. Auth 암호 해시 존재는 기존 비밀번호 로그인 성공을 뜻하지 않는다.
- 역할 소유자·ACL, 관리형 확장·Vault 키, Auth/메일/OAuth 설정, Storage 파일 API, Realtime·Cron·웹훅, Vercel 환경과 브라우저 검증은 이번 복원에서 제외됐다. 백업 이후 변경분은 복구 범위 밖이며 보장 RPO/RTO는 미확정이다.

- 자동 시작 운영 검사는 화면 이동·새로고침 및 입력값 비교였다. 운영에 대기/진행 작업을 인위적으로 만들거나 DB 전수 불변을 검사한 것은 아니다.
- 후속 운영 로그인 API와 인증된 조회는 실제 계정으로 측정해 정상 응답을 확인했다. 실제 브라우저 클릭부터 표시 완료까지의 운영 시간은 아직 별도 과제다.
- 최신 브라우저 회귀 18개는 실제 화면 컴포넌트와 모의 API를 사용한 격리 검사다. 운영 DB까지의 브라우저 통합 검사로 확대 해석하지 않는다.
- 재개 운영 검증은 미인증307→로그인, 실험실 로그인200, 세 상태 GET200, 없는 작업404다. 운영의 실제 재개 성공·유료 생성은 검사하지 않았다. 현재 미완료 배치는 재시도될 수 있고 외부 AI 호출까지 exactly-once를 보장하지 않는다.
- 리전 변경 전후 총 11요청씩 모두 200이었다. DB 서비스 처리 시간과 네트워크 왕복을 함께 해석했으며 upstream 지표를 순수 SQL 실행시간이라고 보지 않는다.
- 전체 테스트 217개·관련 권한/로그인/계측 23개·브라우저 11개와 CI가 리전 배포에서 통과했다.
