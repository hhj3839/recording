# 기록샘 운영·백업·복구 절차

## 적용 범위

소수 교사 비공개 운영 환경의 Supabase 데이터와 Vercel 배포를 대상으로 함. 실제 복구는 대상 프로젝트와 복구 시점을 다시 확인한 뒤 수행함.

## 확인된 운영 구성

- 2026-08-11 기준 `recording` 프로젝트는 Supabase Free 요금제를 사용함.
- 프로젝트 리전은 Oceania(Sydney), `ap-southeast-2`임.
- Free 요금제에는 자동 백업이 없고 현재 생성된 백업도 없음.
- PITR은 활성화되지 않았으며 현재 운영 범위에서는 유료 전환하지 않음.
- 데이터는 `교사 계정 → 학년도·학기별 학급 → 학생·평가계획·평가수준·교과 평어·행동특성` 구조로 보관함.
- 한 계정이 한 학기에 완성하는 자료 1세트를 기본 보관 단위로 삼고, 다음 학기는 새 학급을 만들어 분리함.

## 정기 확인

- 매월 Supabase Database Backups 화면에서 최근 백업 시각과 보존 기간을 확인함.
- 자동 백업이나 PITR이 제공되지 않으면 학기말 작업 시작 전과 종료 후 논리 백업을 생성함.
- 개인정보가 포함된 백업을 공개 저장소, 메신저 또는 일반 공유 폴더에 올리지 않음.
- 환경 변수와 Supabase 키를 백업 파일에 평문으로 포함하지 않음.
- 배포 후 GitHub `main`과 Vercel Production의 커밋 SHA가 같은지 확인함.
- GitHub `main` 푸시와 Pull Request에서 CI의 `Lint`, `Test and build`가 모두 통과했는지 확인함.
- CI는 운영 계정, Supabase 서비스 키, OpenAI API 키를 사용하지 않으며 운영 스모크·E2E·부하 검사를 자동 실행하지 않음.

## 수동 논리 백업 준비 상태

2026-08-11 비파괴 사전 점검 결과는 다음과 같음.

- 로컬에 `pg_dump`가 설치되어 있지 않음.
- Supabase CLI가 설치되어 있지 않음.
- `.env.local`에는 앱 실행용 Supabase URL과 서비스 역할 키가 있으나 PostgreSQL 직접 접속용 `DATABASE_URL` 또는 `DIRECT_URL`은 없음.
- 따라서 운영 데이터 내보내기와 복원 리허설은 아직 실행하지 않았으며, 백업이 존재한다고 판정하지 않음.
- 서비스 역할 키만으로 데이터베이스 전체 구조·함수·정책을 완전하게 논리 백업할 수 있다고 간주하지 않음.

### 파일럿 전 1회 준비

1. PostgreSQL 공식 클라이언트를 설치하고 `pg_dump --version`과 `pg_restore --version`을 기록함.
2. Supabase 대시보드에서 운영자가 직접 단기 데이터베이스 접속 정보를 확인함. 접속 문자열이나 비밀번호를 Git, 문서, 채팅, 셸 기록에 남기지 않음.
3. Git 저장소 밖의 접근 제한 폴더를 백업 대상으로 지정하고, 백업 파일명에 프로젝트·UTC 시각·스키마 버전을 기록함.
4. `pg_dump`의 custom 형식으로 스키마와 데이터를 함께 내보내고 명령 종료 코드, 파일 크기, SHA-256 해시를 기록함.
5. 운영 프로젝트에 복원하지 않고 별도 임시 PostgreSQL 또는 승인된 임시 Supabase 프로젝트에 `pg_restore`함.
6. 테이블·함수·RLS 정책 수와 핵심 테이블의 행 수를 운영 읽기 전용 집계와 대조함.
7. 복원된 환경에서 로그인·사용자 격리·학급 로딩을 검증하고, 임시 환경 정리는 별도 삭제 승인을 받은 뒤 수행함.

### 백업 성공 판정

- `pg_dump` 종료 코드가 0이고 파일이 0바이트보다 큼.
- SHA-256 해시와 생성 시각을 별도 운영 기록에 남김.
- `pg_restore --list`가 오류 없이 백업 목차를 읽음.
- 별도 환경 복원 후 핵심 테이블 행 수와 `owner_id`·`class_id` 격리 검사가 일치함.
- 위 네 조건을 모두 충족하기 전에는 복구 가능한 백업으로 표시하지 않음.

## GitHub·Vercel 배포 확인

1. GitHub Actions `CI`가 성공했는지 확인함.
2. 같은 커밋의 Vercel 상태가 `Deployment has completed`인지 확인함.
3. `https://giroksam-recording.vercel.app/`가 로그인 화면으로 정상 응답하는지 확인함.
4. CI 또는 Vercel이 실패하면 해당 커밋을 운영 완료로 기록하지 않음.
5. 운영 데이터가 필요한 스모크·E2E·AI 검사는 자동 배포와 분리하고 명시적으로 승인된 경우에만 실행함.

유료 교과 부하 검사는 규모별로 `RUN_COMMENT_5_TEST=YES`, `RUN_COMMENT_25_TEST=YES`, `RUN_FULL_225_TEST=YES` 확인값을 요구함. 행동특성 데이터 입력·유료 검사는 각각 `SEED_BEHAVIOR_TEST_DATA=YES`, `RUN_BEHAVIOR_5_TEST=YES`, `RUN_BEHAVIOR_25_TEST=YES`를 요구함. 임시 학급 생성·삭제가 포함된 운영 E2E는 `E2E_ALLOW_PRODUCTION_WRITES=YES`가 없으면 전체 건너뛰며, 실제 AI 구간은 추가로 `E2E_RUN_AI=1`이 있어야 실행함.

GitHub `main` 브랜치는 관리자에게도 `build-and-test`와 `Vercel` 상태 성공을 필수로 요구함. 병합 전 최신 `main` 기준 검사를 다시 통과해야 하며, 해결되지 않은 PR 대화가 있으면 병합하지 않음. 강제 푸시와 브랜치 삭제는 차단함. 현재 소수 운영 방침에 따라 별도 승인 인원 수는 요구하지 않되, 변경은 브랜치와 PR을 통해 병합함.

GitHub Actions는 외부 Action을 전체 40자 커밋 SHA로 고정해야 실행되도록 저장소 수준에서 강제함. 워크플로 내부 자동 검사도 같은 정책을 확인하므로, 새 Action을 추가할 때는 공식 릴리스 태그가 가리키는 커밋 SHA를 확인하고 같은 줄 주석에 릴리스 버전을 기록함.

Vercel Production 배포 성공 이벤트 뒤에는 GitHub Actions `Production health`가 자동 실행됨. 이 검사는 자격증명 없이 공개 로그인·개인정보·약관 페이지의 응답과 민감 조회 API의 비로그인 차단만 확인함. 로그인, 데이터 조회·생성·수정·삭제, OpenAI API 호출은 수행하지 않음.

## 의존성 공급망 점검

- CI의 `Check dependency sources and integrity` 단계는 직접 Git·URL·로컬 파일 의존성을 차단하고 잠금파일의 모든 레지스트리 패키지에 SHA-512 무결성 값이 있는지 오프라인으로 검사함.
- 외부 감사 서비스에 비공개 저장소의 의존성 목록을 전송하지 않음.
- GitHub Dependabot alerts는 2026-07-27 활성화했으며 활성화 직후 열린 경고는 0건이었음.
- 자동 보안 수정과 자동 의존성 업데이트 PR은 활성화하지 않음.
- Dependabot 경고 수는 배포 전과 매월 확인하고, 새 경고가 있으면 영향 범위와 수정 버전을 검토한 뒤 잠금파일을 의도적으로 갱신함.

## 비밀정보 유출 방지

- GitHub Secret scanning과 Push Protection이 모두 활성화되어 있음.
- CI의 `Check tracked files for secrets`는 추적 파일에서 OpenAI·GitHub·Google·AWS 토큰, 개인키, 실제 서비스 키 환경변수 할당 패턴을 오프라인으로 검사함.
- 검사 실패 시 비밀값은 로그에 출력하지 않고 파일명과 유형만 표시함.
- `.env.local`과 로컬 자격증명은 Git에 추가하지 않으며 GitHub Actions에도 운영 키를 등록하지 않음.

## 장애 발생 시

1. 신규 AI 생성과 평가계획 초기화를 중단함.
2. 배포 SHA, 발생 시각, 영향 계정·학급, 오류 메시지를 기록함.
3. 다른 사용자 데이터가 보이면 서비스를 즉시 제한함.
4. 읽기 전용 조회로 손상 범위를 확인하고 복구 전 현재 상태를 별도 백업함.

## 복구 순서

1. 단일 평가계획 변경은 앱의 평가계획 버전 복원을 우선 사용함.
2. 광범위한 손상은 Supabase 백업 시각과 사고 시각을 비교함.
3. 가능하면 임시 프로젝트에 먼저 복원함.
4. `owner_id`, `class_id`, 학생·평가계획·평가수준·생성 결과 수를 대조함.
5. 검증한 범위만 운영 프로젝트에 반영함.
6. 로그인·데이터 격리·권한 스모크 테스트 후 서비스를 재개함.

## 복구 검증

```powershell
pnpm test
pnpm test:smoke
```

비로그인 민감 API, 다른 학급 식별자, 작업 서명 위조, 삭제 확인 문구 우회가 모두 차단되어야 함. 이 검사는 OpenAI API를 호출하지 않음.

## 운영자가 확인해야 할 항목

- Free 요금제 유지 중 자동 백업이 없다는 운영 위험의 정기 재확인
- `ap-southeast-2` 리전에 대한 개인정보 국외 처리 고지 반영 여부
- 복구 담당자와 비상 연락 방법
- 학년도 종료 후 데이터 삭제 일정
- PostgreSQL 클라이언트 설치와 직접 접속 정보 준비
- 파일럿 전 실제 백업·별도 환경 복원 리허설 승인

요금제·백업·PITR·리전은 2026-08-11 대시보드에서 읽기 전용으로 확인했으며, 설정 변경이나 복구 작업은 수행하지 않았음.
