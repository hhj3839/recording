# Auth 미연결 교사·학급 읽기 전용 조사

기준일: 2026-11-03, Asia/Seoul. 대상은 운영 recording과 2026-10-30 20:53:24 KST 백업을 복원한 로컬 PostgreSQL이다. 운영·복원본 모두 `BEGIN READ ONLY`에서 조회했다. 데이터 삭제, 소유권 변경, 재마이그레이션, 실제 로그인은 수행하지 않았다. 로컬 서버는 검증 후 종료했다.

## 결론과 대조 결과

두 행은 최근 복원으로 생긴 손상이 아니라 **UUID 소유권 도입 이전의 이메일 기반 자료가 NULL 소유자로 남은 경우와 부합한다.** 이는 코드와 시점에 근거한 원인 추론이며 당시 쓰기 감사 기록으로 최초 생성 요청을 특정한 결과는 아니다.

| --- | --- |
| 미연결 교사 | 1건, user_id NULL, 생성 2026-07-24 23:49:12.591 KST |

검사한 13개 테이블: students, assessment_plans, assessment_levels, assessment_plan_versions, assessment_plan_pool_links, generated_comments, generated_comment_parts, student_behaviors, generation_jobs, ai_usage_events, record_revisions, classroom_collaborators, pilot_feedback. 현재 public 스키마에서 class_id/classroom_id 열을 조사하여 목록을 정했다. JSON 안의 임의 참조나 외부 로그까지 전수 검사한 것은 아니다. 이메일·학교명·UUID·행 지문 원문은 공개 문서에 넣지 않는다.

초기 로컬 지문은 서버 시간대 차이로 운영과 달랐으나, UTC 설정 후 일치했다. 데이터 변경 증거로 해석하지 않는다. 이 비교는 두 대상 행과 연결 건수에 한정되며 운영 DB 전체 동일성을 뜻하지 않는다.

## 원인 근거와 불확실성

- 2026-07-25 커밋 `e048897`의 `supabase/0002_auth_ownership.sql`은 nullable UUID 열을 추가하고, Auth에 같은 이메일이 있는 행만 UUID로 연결한다. 미일치 행을 삭제하거나 NOT NULL로 제한하지 않는다.
- 그 이전 `app/data-scope.ts`는 이메일 기준으로 교사·학급을 생성/조회했고 UUID 소유자 필드를 쓰지 않았다. 대상 행의 생성 시각은 해당 변경 이전이다. 8월 26일 복원 문서에도 Auth 미연결 빈 학급이 기록돼 있다.
- 현재 확인된 NULL은 “존재하지 않는 UUID를 가리키는 외래키 위반”과 다르다. 연결된 Auth 사용자의 정상 삭제는 CASCADE로 해당 행도 삭제하므로, 정상 사용자 삭제만으로 지금의 NULL 행이 생겼다고 볼 근거는 없다.
- 다만 생성 시각은 앱이 쓰는 값이고 당시 DB 마이그레이션 실행 시각·Auth 생성/삭제 이력·수동 수정 기록을 확보하지 못했다. 최초 작성자, 당시 Auth 이메일 일치 여부, 수동 NULL 변경 가능성은 확정하지 않는다.

## 접근 및 기능 영향

- `getAuthUser()`는 Auth 서버의 getUser 결과로 신원을 확인한다. 현재 학급 목록·선택·삭제와 `getDataScope()`는 인증된 UUID의 owner_id 조건을 사용한다. NULL 소유자 학급은 정상 소유 학급 조회에 포함되지 않는다. 교사 프로필 변경도 user_id 조건을 사용한다.
- 대상 학급의 학생·결과·작업·협업·이력은 조사한 13개 테이블에서 0건이다. 이 두 행 때문에 현재 학생 결과가 유실되거나 다른 사용자에게 노출됐다는 증거는 확인하지 못했다. 실제 운영 권한 E2E나 직접 REST 역할 검증을 수행한 것은 아니다.
- **향후 같은 이메일의 계정 생성 시 주의:** 학급 생성 및 최초 학급 준비는 `owner_email,school_year,semester,grade,class_number` 충돌 키로 upsert한다. 같은 이메일·기간·반 조합의 계정이 준비되면 기존 NULL 학급의 owner_id가 새 UUID로 갱신될 수 있고, 교사도 이메일 충돌 키로 연결될 수 있다. 이는 현재 존재하는 계정의 접근 성공 증명이 아니라 코드에서 확인한 조건부 경로다. 이를 정정 수단으로 삼아 로그인/가입을 시도하지 않는다.
- 서버의 service-role 조회는 RLS에만 의존하지 않으므로 소유권 조건을 계속 유지해야 한다. 기존 data-scope 격리 회귀 9개는 통과했다. 이 검사는 모의 DB를 사용하며 해당 레거시 행의 실제 upsert 재현이나 운영 로그인 검증을 대체하지 않는다.

## 보존·정정 선택안

1. **현재 권고: 보존.** NULL 두 행을 변경하지 않고 조사 기록으로 관리한다. 연결 자료가 없고 현재 Auth와 일치하지 않으므로 즉시 삭제·임의 계정 연결의 필요성은 확인되지 않았다. 다음 정기 점검에서는 NULL 건수·자식 건수·동일 이메일 Auth 발생 여부를 읽기 전용으로 재확인한다.
2. **정당한 소유자가 확인되는 경우에만 정정 검토.** 이메일 문자열만으로 소유자를 결정하지 않는다. 계정 본인 확인, 자료의 실제 소유 근거, 기간/학급 중복, 다른 UUID 연결 여부를 확인하고 대상 PK·기존 지문·NULL 조건을 명시한 변경안을 별도로 승인받는다. 실행한다면 트랜잭션에서 조건부 갱신과 영향 행 수 검증, 자식 자료 재검사, 복구 사본 및 롤백안을 갖춘다. 이번에는 SQL 변경안을 실행하지 않았다.
3. **불필요한 시험 자료로 확정되는 경우:** 보존 기간과 별도 삭제 범위를 합의한 후 삭제를 검토한다. “비어 있음”만으로 삭제하지 않으며 CASCADE 영향·새 참조를 실행 직전에 다시 확인한다.
4. **예방 개발안:** 같은 이메일 충돌 upsert가 NULL/다른 UUID 학급을 묵시적으로 연결하는 경로를 별도 격리 테스트로 재현하고, 계정 준비와 명시적 레거시 인계를 분리하는 방안을 검토한다. 현재 두 행의 변경 없이 구현·권한 회귀를 먼저 설계한다. 이번 조사만으로 권한 취약점 악용이나 사고 발생을 확정하지 않는다.
